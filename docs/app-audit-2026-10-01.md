# Application audit — 2026-10-01

Scope: current working tree, including existing uncommitted Docker and production configuration changes. Reviewed controllers, policies, models, jobs, AI services, views/JavaScript, database schema, deployment and CI. No application fixes were made. Findings below are based on code inspection unless a check is explicitly noted. This is not a deployed penetration test or a complete dependency advisory scan.

## High priority

1. **Production exposes unauthenticated infrastructure.** `docker-compose.yml:144-169` publishes PostgreSQL, Redis and Elasticsearch on all host interfaces. The production overlay retains these mappings (confirmed with merged Compose configuration). Elasticsearch explicitly disables security; Redis has neither authentication nor a persistent volume. An accessible host permits direct index access, data modification and job-queue manipulation. Remove infrastructure port mappings from production; bind development mappings to loopback. Persist Redis job data and configure an appropriate persistence policy.

2. **Seeds create and reset a known admin credential.** `db/seeds.rb:8-13` assigns `password1234` to `admin@department.com`, skips confirmation and executes in every environment. Re-running seeds resets that account's password. Fresh database preparation can invoke seeds. Restrict demo users to development/test; provision production administrators through a separate explicit process without a fixed password.

3. **Stored HTML injection in tag suggestions.** `app/javascript/controllers/tag_input_controller.js:265-277` inserts `tag.name` directly into HTML text and a quoted attribute. `TagsController#create` accepts names from any authenticated user, and `Tag` does not restrict markup. A name containing HTML or quotes can change the suggestion DOM for other users, including administrators. The current CSP blocks common inline-script payloads, so script execution was not demonstrated; the injection itself is present. Construct DOM nodes with `textContent` and `dataset`, or escape both insertion contexts. Add a browser regression check with hostile tag names.

4. **AI moderation decisions can approve changed or withdrawn content.** `app/jobs/moderate_post_job.rb:30-51` and `app/jobs/moderate_post_revision_job.rb` inspect state before a network call, then apply its result without checking a content digest, review generation or current moderation state under a lock. An author can edit an unverified post while a review runs; the old decision can verify its newer database content. A revision can be withdrawn while its job runs and still be approved. Human rejection can also be overwritten. Capture an immutable review snapshot and apply results only after a locked state/version comparison.

5. **Rails is below published security patch releases.** `Gemfile.lock:315` pins Rails 8.0.4. Rails maintainers published 8.0.4.1 addressing ten security issues, including potential XSS vulnerabilities, on March 23, 2026. Upgrade to a current supported patched release and scan all locked dependencies. This establishes a missing security update, not exploitability of every advisory in this app. Source: https://rubyonrails.org/2026/3/23/Rails-Versions-7-2-3-1-8-0-4-1-and-8-1-2-1-have-been-released

## Medium priority

6. **Revision creation bypasses pending-review edit restrictions.** `app/controllers/post_revisions_controller.rb:14-32` reuses `active_revision` but authorizes `create?`, which checks post ownership and publication rather than the revision state. Posting to the create endpoint can overwrite a pending revision or return it to draft, although the update policy prohibits editing pending revisions. Authorize the existing revision with `update?`; enforce transitions in the model. This also amplifies finding 4.

7. **Approval/rejection lacks state transition guards.** `app/models/post_revision.rb:52-86` allows approval of draft, rejected and already approved revisions, and rejection of approved revisions. Admin endpoints authorize only the administrator role. Replayed or stale requests can overwrite newer live content or make revision status disagree with the applied post. Require a pending state, lock relevant rows and make repeated transitions explicit/idempotent.

8. **Deleted posts remain in the search index.** Post disables Searchkick callbacks and has no destroy callback, and `PostSearchIndexJob` returns when the record is absent. Deleted documents remain indexed, can affect counts and search pages, and retain their indexed content. Explicitly delete the search document on destroy and test deletion followed by search.

9. **Paid AI requests have no application quota or input-size bound.** `app/controllers/chat_controller.rb:6-11` accepts an arbitrarily long message and queues work for every request. `ChatHistory` validates presence only, and no application throttling was found. Any confirmed account can consume provider budget, queue capacity and storage. Bound message size and add per-user rate/concurrency limits and a deployment budget control. External gateway controls were not assessed.

10. **No automated application tests execute.** `bundle exec rails test` reports zero runs and zero assertions; the `spec/requests` directory is empty. CI invokes Rails test commands, but also has no PostgreSQL service despite using PostgreSQL in test configuration. Add meaningful authorization, revision-transition, stale moderation, tag rendering and production-boot checks; provision pgvector PostgreSQL and any required test services in CI. A green empty test command gives no behavior assurance.

11. **Full search reindex is on the server startup path by default.** `bin/docker-entrypoint:33-47` prepares the database, waits for Elasticsearch and synchronously rebuilds both indexes before starting the server. Production inherits `REINDEX_ON_BOOT=true`. Larger indexes or an unavailable search service delay or prevent web startup; multiple replicas can race reindexes. Disable routine full boot reindexing and run maintenance as a separate explicit operation.

12. **Suspension cleanup can clear a newly extended suspension.** `app/jobs/clear_expired_suspensions_job.rb:7-13` reads expired IDs and later clears those IDs without rechecking their expiry. An administrator extending a suspension between those statements loses the new suspension. Apply the expiration predicate again on the update, or lock rows and update atomically. Production also schedules this through both Sidekiq cron and Solid Queue, adding redundant work.

## Operational observations

- Production Compose starts a plain HTTP Rails server on ports 80 and 3000 while assuming an SSL-terminating proxy. No TLS proxy is defined in this stack. An external proxy is required for the default HTTPS configuration; direct Compose deployment alone does not provide TLS.
- `SOLID_QUEUE_IN_PUMA` starts an additional queue system while Active Job uses Sidekiq. Its presence test enables the plugin even for the string `false`. Choose deliberate scheduler ownership and parse the variable as a boolean.
- Avatar uploads have no model size/type validation; thumbnails have a size check but no image-type restriction. Set limits consistent with supported image processing and storage budgets.
- `comments_visible` is uncapped, reply branches are unpaginated, and comment bodies lack a length cap. Large threads can generate expensive responses. Bound request-controlled counts and paginate replies.
- Local uploads require backup/restore procedures and shared storage if scaling beyond one host. No backup automation was identified in the reviewed repository.
- The Docker entrypoint detects `rails server` but not the Dockerfile's default `./bin/rails server` spelling, so direct image startup skips its preparation function. Compose's overridden command matches the detector.
